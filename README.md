# 잘자요 · Jaljayo

누운 채 말로 침대 자세를 조절하고, 목적별 자세를 기억하는 온디바이스 AI 모션베드 프로젝트입니다.

폰 설정 앱, 보드 Android 앱, 침대 시연 화면, AI 학습 코드, 센서 코드를 하나의 저장소에서 관리합니다. 여기서 백엔드는 외부 인터넷 서버가 아니라 **보드 안에서 명령을 처리하고 상태를 저장하는 코드**입니다.

> **저장소 안내**: 조직은 `Hansung-Jaljayo`, 저장소 이름은 `Jaljayo`입니다. 아래 폴더 구조와 협업 규칙은 적용할 구성안이며, 현재 폴더 생성·브랜치 보호 설정·기능 구현이 완료됐다는 뜻은 아닙니다.

### 담당 경계

- **각도와 이동 상태를 바꾸는 공통 처리는 Backend 1이 담당합니다.** Backend 2는 알람·예약에서 이동을 요청하고, Frontend 2는 보드 상태를 받아 표시합니다.
- **기기 등록과 승인 상태 관리는 Backend 1이 담당합니다.** Backend 2는 승인에 사용할 물리 버튼 입력을 전달합니다.
- Backend 1과 Backend 2는 `board-app/`을 함께 사용하되 위 기능별로 작업을 나눕니다. 실제 패키지·파일 경계는 프로젝트 구조를 확인한 뒤 정합니다.
- 웹 화면 소스는 `demo-web/`에만 둡니다. 보드 앱에 넣는 빌드 결과와 웹 원본을 따로 수정하지 않습니다.
- 학습 문장 작성과 교차 검토는 전원 공통입니다. 온디바이스 AI의 취합·검사는 학습 데이터에 대한 업무이며, 팀 전체 코드·문서를 혼자 취합한다는 뜻이 아닙니다.

## 3. 작업 순서

1. **처음 한 번:** 조직 저장소 접근 권한을 받은 뒤 저장소 전체를 Clone합니다. 자기 폴더만 다운로드하면 팀의 변경 이력을 함께 관리할 수 없습니다.
2. **작업 시작:** 이전 작업을 커밋하거나 안전하게 보관한 상태에서 `dev`로 이동해 최신 변경을 가져옵니다. 남은 수정 사항을 지우면서 이동하지 않습니다.
3. **브랜치 생성:** 최신 `dev`에서 이번 작업용 브랜치를 만듭니다. 예: `feat/phone-alarm-list`.
4. **구현·확인:** 본인 담당 파일을 수정하고 해당 파트가 빌드·실행되는지 확인합니다. 구체적인 실행 명령은 각 파트의 `docs/setup/` 안내를 따릅니다.
5. **커밋:** 변경 목록을 보고 이번 작업에 필요한 파일만 선택해 커밋합니다. 비밀번호·개인 설정·빌드 결과가 섞이지 않았는지 확인합니다.
6. **푸시:** 작업 브랜치를 GitHub에 올립니다.
7. **PR 생성:** 합칠 대상인 **base는 `dev`**, 수정한 쪽인 **compare는 본인 작업 브랜치**로 지정합니다. 제목과 변경 내용을 작성합니다.
8. **본인이 병합:** 충돌이 없고 필요한 확인을 마쳤으면 팀원 승인을 기다리지 않고 본인이 `dev`에 병합합니다. 작업 브랜치는 Squash merge로 합칩니다.
9. **다음 작업:** 병합된 작업 브랜치를 계속 쓰지 말고, 최신 `dev`에서 새 브랜치를 만듭니다.

### 충돌이 나면

- 어느 파일에서 충돌했는지 확인하고 관련 담당자에게 PR에서 `@GitHub아이디`로 알립니다. 역할에 해당하는 담당자의 GitHub 아이디를 사용합니다.
- 두 사람의 변경 의도를 확인한 뒤 필요한 내용을 합칩니다. 내 코드나 상대 코드 중 하나를 무조건 선택하지 않습니다.
- 해결한 내용을 다시 확인·커밋·푸시한 뒤 병합합니다. 모르겠으면 삭제하거나 강제 푸시하지 말고 도움을 요청합니다.
- 담당자에게 자동으로 충돌 알림이 가는 설정은 아직 없습니다. 직접 알려야 합니다.

**충돌이 없어도 통신 규격이나 명령 토큰을 바꾸면 연결되는 담당자에게 알립니다.** 파일이 겹치지 않아도 서로 기대하는 값이 달라지면 기능이 연결되지 않습니다.

## 4. 브랜치 규칙

| 브랜치 | 용도 | 병합 규칙 |
| --- | --- | --- |
| `main` | 제출·배포할 안정 버전 | `dev`에서 PR을 만들고 다른 팀원 1명 승인 후 Merge commit으로 병합 |
| `dev` | 팀 작업을 합치는 통합 개발 버전 | 각자 작업 브랜치에서 PR을 만들고 본인이 Squash merge. 승인 필수 아님 |
| 작업 브랜치 | 한 가지 기능·오류·문서 작업 | 최신 `dev`에서 생성하고 병합 후 삭제 |

Squash merge는 작업 중 생긴 여러 커밋을 하나로 묶어 합치는 방식입니다. Merge commit은 두 브랜치의 이력을 연결해 합치는 방식입니다. 최초 설계서 변환 PR에는 내용 개선을 섞지 않아 최초 MD 상태가 독립된 커밋으로 남게 합니다.

`main`과 `dev`에는 직접 푸시하지 않고 PR을 사용합니다. 두 브랜치의 강제 푸시와 삭제는 차단하는 것을 기준으로 설정합니다. 이 문서에 적었다고 GitHub 설정이 자동 적용되는 것은 아닙니다.

### 작업 브랜치 이름

`종류/파트-작업내용` 형식으로 영문 소문자와 하이픈을 씁니다. 사람 이름보다 작업 내용을 적습니다. 다음은 명명 제안입니다.

| 종류 | 언제 쓰나 | 예시 |
| --- | --- | --- |
| `feat` | 새 기능 | `feat/phone-alarm-list` |
| `fix` | 오류 수정 | `fix/board-stop-handling` |
| `refactor` | 동작을 유지하는 코드 정리 | `refactor/board-command-router` |
| `docs` | 문서 수정 | `docs/design-markdown` |
| `test` | 테스트 추가·수정 | `test/ai-command-evaluation` |
| `chore` | 환경·의존성·도구 설정 | `chore/web-build-setup` |

여러 파트에 걸친 작업은 `feat/alarm-sync`처럼 파트를 생략할 수 있습니다. `feat/`와 `feature/`를 혼용하지 않습니다.

## 5. 커밋 메시지와 PR

커밋 메시지는 `종류(파트): 변경 내용`으로 적습니다. 설명은 한국어로 쓰며, 종류는 위 브랜치 표와 같습니다. 파트는 `phone`, `board`, `web`, `ai`, `firmware`, `design`, `repo`를 사용합니다.

```text
feat(phone): 알람 목록 화면 추가
fix(board): 정지 후 이전 이동 명령이 재실행되는 문제 수정
docs(design): 상세설계서 PDF를 내용 변경 없이 MD로 이전
test(ai): 대상 없는 취소 발화 평가 사례 추가
chore(web): 시연 화면 빌드 설정 추가
```

한 커밋에는 관련된 변경을 묶습니다. 기능 코드와 그 테스트·설명은 함께 넣어도 되지만, 관계없는 오류 수정은 분리합니다. `수정`, `최종`, `진짜최종`만으로 메시지를 쓰지 않습니다.

PR 제목도 같은 형식으로 적습니다. 본문은 아래 형식을 사용합니다. 예시의 파일명은 실제 변경 파일로 바꿉니다.

```markdown
## 작업 내용
### 알람 목록 화면 추가
저장된 알람의 시각과 활성 상태를 목록에 표시하도록 구현했습니다.
## 변경 파일
- phone-app/실제수정파일.kt
```

## 6. 문서 기준과 최초 버전 보존

- `docs/design.md`: 현재 동작 규칙을 설명하는 상세설계서입니다. 최신 PDF 전체를 그대로 옮겨 대조한 최초 MD 상태를 별도 커밋으로 남깁니다. 이후 이 파일을 수정하며 Git 이력으로 변경 내용을 비교하고 이전 버전을 복구합니다.
- 최초 버전을 보관하기 위해 같은 MD를 두 벌 만들지 않습니다. 기존 PDF는 로컬에 보관하고 백업만을 위해 레포에 넣지 않습니다.
- `docs/interfaces/`: 코드가 주고받는 명령·필드·자료형·응답을 기록합니다. 사용자 동작 규칙을 중복해서 길게 적지 않고 상세설계서의 관련 부분을 참조합니다.
- 기획안·최종 수행계획서는 이번 MD 변환 대상이 아닙니다. `docs/plans/`에는 별도로 공개하기로 정한 문서만 넣습니다.

## 7. 공개 저장소에 올리는 파일

이 저장소는 Public이므로 올린 파일과 커밋 이력이 외부에 보일 수 있습니다.

- 역할 중심으로 소개하고 학번·전화번호·개인 이메일이 포함된 제출본은 그대로 올리지 않습니다.
- 마음AI 제공 코드·데이터·모델은 공개 조건을 확인한 것만 포함합니다. 파일이 작다는 이유로 공개 가능한 것은 아닙니다.
- 비밀번호, API 키, 인증 토큰, 서명 키, 개인 환경 설정은 커밋하지 않습니다.
- 모델 가중치와 대용량 생성물은 일반 소스 커밋에 넣지 않고 보관 방법을 별도로 정합니다. 공개 Releases도 외부 공개 공간입니다.
- `.gitignore`는 앞으로 추적하지 않을 파일을 지정합니다. 이미 커밋한 파일이나 과거 이력까지 지워주는 기능은 아닙니다. 잘못 올렸다면 혼자 강제 푸시하지 말고 팀에 즉시 알립니다.

## 8. 개발 환경 안내

파트별 실제 프로젝트 구조와 실행 환경을 확인한 뒤 `docs/setup/`에 설치·실행 방법을 작성합니다. 아직 확인하지 않은 빌드 명령이나 모델 실행 절차를 성공한 방법처럼 안내하지 않습니다.

현재 저장소에는 README만 등록되어 있습니다. 위 폴더 구조는 구성 예정이며, 브랜치 보호 설정은 아직 적용하지 않았습니다.
